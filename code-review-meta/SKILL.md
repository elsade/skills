---
name: code-review-meta
description: Run a meta code review that fans out to architecture, code-quality, Clean Code, simplification/efficiency, comment-verbosity, and Codex reviewers (plus conditional API-design, database, Terraform, Kubernetes, Docker, and observability reviewers), aggregates findings into a prioritized fix list, clarifies ambiguities, then offers to resolve.
argument-hint: "[PR number | empty for local branch vs main]"
allowed-tools: Read, Glob, Grep, Bash(git:*), Bash(gh:*), Bash(codex:*), Bash(node:*), Agent, Skill, Edit, Write
---

Review the following scope.

Scope resolution:
- If argument is a positive integer → **PR mode**: review GitHub PR #N in the current repo (use `gh pr view` and `gh pr diff`).
- If argument is empty → **Local branch mode**: review the current branch against `origin/main` (base = `git merge-base HEAD origin/main`).
- Anything else → ask the user to clarify before proceeding.

Then:
1. Resolve the diff.
2. Dispatch reviewers **in parallel** (one message with all applicable Agent tool calls):
   - **Architecture** — `general-purpose`, using the `architecture-patterns` skill. Flag boundary violations, leaky abstractions, coupling issues, misplaced logic. No style or small-bug comments.
   - **Code quality / craft** — `code-reviewer` (superpowers:code-reviewer). Correctness, maintainability, security, test coverage, project conventions.
   - **Clean Code (Uncle Bob)** — `general-purpose`, using the `uncle-bob-craft` skill. Flag SOLID violations, function size/complexity, naming clarity, abstraction levels, side effects, command-query separation. Craftsmanship and readability only — not architecture or correctness bugs.
   - **Simplification / efficiency** — `general-purpose`, same lens as the `/simplify` command but review only. Flag redundant/duplicated logic that should reuse existing code, unnecessary abstraction, dead code, and wrong-altitude changes (over-engineered or missing an obvious simplification). Not correctness, security, or naming/SOLID — those are covered by other reviewers. Return findings, do not edit files.
   - **Comment verbosity** — `general-purpose`, using the `clean-code` skill's Comments criteria. Look only at comments newly added or modified by this diff — not pre-existing ones. Prefer clear names, small functions, and straightforward control flow over explanatory comments. For every introduced comment, question whether it's needed at all: it earns its place only if it explains *why* — a hidden constraint, a non-obvious reason, a tradeoff, a workaround, surprising behavior, an external requirement, or a decision a future maintainer might otherwise undo — never if removing it would leave the code equally clear. For each one that fails that test, give a concrete shorter-but-correct replacement (trimmed text, or "delete — code is self-explanatory" with why). Flag comments that are redundant, noise, outdated, position markers or unnecessary section headings, multi-line where one line would do, that repeat names already in the code, or that narrate WHAT the code does instead of WHY. When a comment exists to compensate for unclear code, don't just cut it — suggest the concrete rename or restructure that would make the comment unnecessary. Never demand a comment just because code is complex; propose making the code clearer first. Exempt from this test: required legal/license/copyright notices, tool-interpreted directives (lint/type-checker suppressions like `noqa`, `type: ignore`, `eslint-disable`, pragmas), and useful public API documentation — these change tooling behavior, satisfy a notice requirement, or document a contract for callers, not just readability, so never shorten or delete them. Report findings as **low** severity unless a comment is actively misleading or obscures a material issue, which rates higher. Not a correctness or architecture pass; naming and structure suggestions are in scope only as the alternative to a comment.
   - **Codex second opinion** — `codex-rescue` (fallback: `Bash: codex exec --sandbox read-only "<review prompt + diff>"`). Review only, never patch. Correctness bugs, design risks, edge cases the author may have missed.
   - **API design (conditional)** — dispatch only if the diff touches HTTP API surface: route decorators (`@app.get`, `@router`), request/response models used in route signatures, OpenAPI schema files, or nginx/gateway route configs. Use the `api-design-principles` skill; API surface design only.
   - **Database architecture (conditional)** — dispatch only if the diff touches migration files, ORM models (`Column`, `ForeignKey`, `relationship`), repository implementations, or raw SQL/Alembic config. Use the `database-architect` skill; schema/migration/query concerns only.
   - **Terraform (conditional)** — dispatch only if the diff touches `.tf`/`.tfvars`/`.tfvars.json`/`.terraform.lock.hcl` files or `**/terraform/**`, `**/infra/**`, `**/environments/**`. Use the `terraform-specialist` skill. Flag state management, module design, provider pinning, unsafe changes (implicit replacement, missing lifecycle blocks, hardcoded secrets). IaC concerns only.
   - **Kubernetes / GitOps (conditional)** — dispatch only if the diff touches K8s manifests, Helm charts, or GitOps config (`apiVersion:`/`kind:` blocks, `Chart.yaml`, `values*.yaml`, `templates/**/*.yaml`, ArgoCD `Application`, Flux `HelmRelease`/`Kustomization`). Use the `kubernetes-architect` skill. Flag resource limits, pod security context, missing PDB/HPA, GitOps drift risk, Helm templating mistakes.
   - **Docker (conditional)** — dispatch only if the diff touches `Dockerfile`/`Dockerfile.*` or `**/docker/**`. Use the `docker-expert` skill. Flag image size/layer efficiency, multi-stage build opportunities, security hardening (root user, unpinned base images, leaked secrets). Container build concerns only.
   - **Observability / OTel (conditional)** — dispatch only if the diff touches OTel instrumentation or observability config: SDK initialization, span/trace/metric/log code, OTel Collector config files, or telemetry utility modules. Use the `observability-engineer` skill. Flag semantic convention compliance, context propagation correctness, sampling strategy, metric naming/cardinality, log-to-trace correlation, collector pipeline correctness. Observability concerns only.
3. Aggregate and deduplicate findings, preserving source attribution. If reviewers disagree on severity, take the highest and note the disagreement.
4. Apply the `humanizer` skill to every finding's summary and suggested fix before presenting — strip AI writing tells, write like a colleague, keep technical precision.
5. Emit the final markdown report with a recommended fix order.
6. Flag every ambiguity in a `Clarifications needed` section and stop for user input.
7. Only after all ambiguities are answered, offer to resolve. Do not edit files until the user confirms.
